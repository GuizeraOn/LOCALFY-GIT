<objective>
Create `POST /api/sync/hotmart`: a Next.js route handler that authenticates against the Hotmart sales-history REST API with a Bearer token, fetches ONE page of past sales, and upserts them into `sales` and `sale_utms` idempotently, returning the pagination cursor so the caller can walk the full history.

Purpose: The Phase 1 webhook only ever captures sales that happen from now on. HOT-04 requires backfilling everything that already happened, otherwise the dashboard's revenue/ROAS figures are blank for every past date range.

Output: the route handler, an `.env.example` documenting the new credential, and a README section describing how to run the import.
</objective>

<http_contract>
<!-- This is the contract plan 06-03 (dashboard button) consumes. It must not drift. -->

POST /api/sync/hotmart

Request body (application/json), all fields optional:
  startDate: string "yyyy-MM-dd"   (default: today minus 365 days)
  endDate:   string "yyyy-MM-dd"   (default: today)
  pageToken: string                (opaque cursor returned by a previous call)

200 response:
  { "success": true,
    "count": number,          // rows upserted into `sales` in THIS page
    "total": number,          // items returned by Hotmart in THIS page
    "skipped": number,        // items dropped because they had no transaction id
    "nextPageToken": string | null,   // null => import finished
    "totalResults": number | null }   // Hotmart's total across all pages, when provided

400: { "error": "Invalid date format" }            — startDate/endDate not yyyy-MM-dd, or start after end
500: { "error": "Server configuration error" }     — HOTMART_ACCESS_TOKEN not set
401: { "error": "Hotmart authentication failed" }  — Hotmart replied 401/403
502: { "error": "Failed to fetch from Hotmart" }   — any other non-ok upstream reply
500: { "error": "Database error" }                 — Supabase upsert failed
</http_contract>

  <action>
Create `src/app/api/sync/hotmart/route.ts`. The very first statement of the file must be `export const dynamic = 'force-dynamic';` (matching `src/app/api/sync/facebook/route.ts` — commit 6158fda added it precisely to stop the Supabase client from being constructed at build time). Then import `NextResponse` from `next/server`, `supabaseServerClient` from `@/lib/supabase-server`, and `buildSalesHistoryUrl`, `mapHotmartItem`, `dedupeMappedSales`, `extractPageInfo`, plus the `MappedHotmartSale` type, from `@/lib/hotmart`.

Export a single async `POST(request: Request)` handler wrapped in try/catch (the catch logs with `console.error('Hotmart sync error:', error)` and returns 500 `{ error: 'Internal server error' }`, matching the Facebook route).

Handler steps, in order:

1. Parse the body defensively: `await request.json()` inside a try that falls back to `{}` so an empty body is valid (the endpoint must work with no arguments).

2. Read `process.env.HOTMART_ACCESS_TOKEN`. If it is missing or empty, `console.warn('Missing HOTMART_ACCESS_TOKEN environment variable.')` and return 500 `{ error: 'Server configuration error' }`. Never echo the token, its length, or any prefix of it in a response or a log line.

3. Validate dates. Accept `startDate` and `endDate` only when they match the regex `^\d{4}-\d{2}-\d{2}$`; if a provided value fails the regex return 400 `{ error: 'Invalid date format' }`. Compute:
   - `endDateMs` = `Date.parse(`${endDate}T23:59:59.999Z`)` when provided, else `Date.now()`;
   - `startDateMs` = `Date.parse(`${startDate}T00:00:00.000Z`)` when provided, else `endDateMs` minus 365 days in milliseconds (365 * 24 * 60 * 60 * 1000).
   If either parse is `NaN`, or `startDateMs > endDateMs`, return 400 `{ error: 'Invalid date format' }`.

4. Read `pageToken` from the body only when it is a non-empty string; anything else is treated as absent.

5. Build the request URL with `buildSalesHistoryUrl({ startDateMs, endDateMs, pageToken, maxResults: 50 })`. Do not build the URL by hand.

6. Call the API with `fetch(url, { method: 'GET', cache: 'no-store', headers: { Authorization: `Bearer ${token}`, Accept: 'application/json' } })`. The token goes in the Authorization header only — it must never appear in the query string, because query strings are logged by proxies.

7. Handle a non-ok response: read the body with `await response.text()`, log it server-side with `console.error('Hotmart API Error:', response.status, errorText)`, and return to the CLIENT a generic message only — 401 `{ error: 'Hotmart authentication failed' }` when `response.status` is 401 or 403, otherwise 502 `{ error: 'Failed to fetch from Hotmart' }`. Never include `errorText` in the JSON response.

8. Parse the JSON. Read the item array from `payload.items` falling back to `payload.data`, defaulting to an empty array; guard with `Array.isArray`.

9. Map: run every item through `mapHotmartItem`, drop the `null` results (count them into `skipped`), then pass the survivors through `dedupeMappedSales`.

10. Persist, sales first because `sale_utms.transaction_id` is a foreign key to `sales.transaction_id`:
    - Build the sales rows array from `mapped.map(m => ...)` including `transaction_id`, `status`, `price`, `updated_at: new Date().toISOString()`, and `created_at` ONLY when `m.sale.created_at` is non-null (omit the key entirely otherwise, so Postgres keeps the DEFAULT/existing value instead of writing null into the column).
    - When the array is non-empty, one batched call: `supabaseServerClient.from('sales').upsert(saleRows, { onConflict: 'transaction_id' })`. On error, `console.error('Error upserting sales:', error)` and return 500 `{ error: 'Database error' }`.
    - Build the utm rows from `mapped.filter(m => m.utms !== null)` and, when non-empty, upsert into `sale_utms` with `{ onConflict: 'transaction_id' }`. On error, log with `console.error('Error upserting sale_utms:', error)` but do NOT fail the request — the sales rows are already persisted, which mirrors the webhook's behaviour.

11. Compute `const { nextPageToken, totalResults } = extractPageInfo(payload)` and return 200 with exactly `{ success: true, count: saleRows.length, total: items.length, skipped, nextPageToken, totalResults }`.

Scope guard: this handler processes exactly ONE page per request and never loops over pages internally. Pagination is driven by the client (plan 06-03) so a large history cannot exceed the serverless function execution limit and so the UI can report real progress.

Type-safety note: `strict: true` is on and eslint-config-next flags `any`. Type the parsed payload as `unknown` / a narrow local interface and narrow explicitly; type the sales row array as `Record<string, unknown>[]` or a dedicated local interface with the optional `created_at` field.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> `POST /api/sync/hotmart` | Unauthenticated request from the dashboard; body is fully attacker-controllable. |
| Route -> Hotmart REST API | Outbound call carrying the long-lived `HOTMART_ACCESS_TOKEN` secret. |
| Route -> Supabase | Writes with the service-role key, which bypasses row-level security. |
| Repository -> git history | `.env.example` risks committing real credentials. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-06 | Information Disclosure | `HOTMART_ACCESS_TOKEN` handling | mitigate | Token read only inside the route handler (server-only, never a `NEXT_PUBLIC_` var), sent only in the `Authorization: Bearer` header, never in the URL query string, never echoed in a response body or log line. |
| T-06-07 | Information Disclosure | Upstream error propagation | mitigate | Hotmart error bodies are logged with `console.error` server-side only; the client receives fixed strings (`Hotmart authentication failed` / `Failed to fetch from Hotmart`), so upstream account/PII detail cannot be enumerated through the endpoint. |
| T-06-08 | Information Disclosure | `.env.example` | mitigate | Placeholder values only; task acceptance asserts no literal value from `.env.local` appears in `.env.example`, and `git check-ignore` confirms `.env.local` stays ignored. |
| T-06-09 | Tampering / Injection | Request body -> outbound URL | mitigate | `startDate`/`endDate` accepted only after an anchored `^\d{4}-\d{2}-\d{2}$` regex and `Date.parse` sanity check; all query params written through `URLSearchParams` in `buildSalesHistoryUrl`; the API host is a hard-coded constant, so no SSRF redirect target can be injected. |
| T-06-10 | Tampering | Untrusted Hotmart JSON -> Supabase | mitigate | Only allow-listed, coerced fields are written (see plan 06-01 mapping); rows without a transaction id are skipped rather than inserted; the batch is deduped so `ON CONFLICT` cannot abort; supabase-js parameterises all values, so no SQL injection surface. |
| T-06-11 | Denial of Service | Unbounded import work | mitigate | Exactly one upstream page (`max_results` 50) per HTTP request, no server-side pagination loop, `cache: 'no-store'`; a single request therefore has bounded runtime and memory and cannot exhaust the serverless execution limit. |
| T-06-12 | Spoofing / Elevation | Endpoint has no authentication | accept | The route mirrors the existing `POST /api/sync/facebook` posture: the application has no auth subsystem at all and is a single-tenant private deployment. The endpoint returns only aggregate counts (no sale data), and writes only the owner's own Hotmart records into the owner's own database, so the residual risk is upstream API-quota abuse. Residual risk recorded; adding authentication requires an auth subsystem, which is out of scope for HOT-04 and must be planned as its own phase. |
| T-06-13 | Repudiation | Import provenance | accept | Imported rows are indistinguishable from webhook rows (no `source` column exists in the Phase 1 schema). Acceptable because both paths are the same owner's data and `transaction_id` remains the single source of truth; adding provenance would require a schema migration outside this phase's scope. |
| T-06-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs NO packages — it uses the built-in `fetch`, the already-installed `@supabase/supabase-js`, and `next/server`. No `npm install` is permitted; if the executor believes a dependency is needed, stop and escalate rather than install. |
</threat_model>
