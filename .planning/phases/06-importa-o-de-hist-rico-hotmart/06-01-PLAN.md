<objective>
Create the pure, dependency-free mapping layer for the Hotmart sales history REST API, plus an offline harness that proves the mapping is correct without any Hotmart credentials.

Purpose: The riskiest part of importing history is the field mapping (transaction id, status, price, historical date, UTMs). It cannot be tested against the live API during development because it requires a production token. Isolating it as pure functions makes it verifiable and keeps the route thin. This module is the contract that plan 06-02 (the API route) consumes.

Output: `src/lib/hotmart.ts` (mapping contract + implementation) and `scripts/check-hotmart-mapping.mjs` (runnable verification).

<database_contract>
The two target tables already exist (created in Phase 1, `supabase/migrations/0000_initial_schema.sql`). The mapping output MUST match these columns exactly:

sales:
  transaction_id TEXT PRIMARY KEY
  status         TEXT NOT NULL
  price          NUMERIC NOT NULL
  created_at     TIMESTAMPTZ DEFAULT NOW()
  updated_at     TIMESTAMPTZ DEFAULT NOW()   (also set by an UPDATE trigger)

sale_utms:
  transaction_id TEXT PRIMARY KEY REFERENCES sales(transaction_id) ON DELETE CASCADE
  utm_source, utm_campaign, utm_medium, utm_content, utm_term  TEXT NULL

Phase 1 decisions that still bind this phase:
- D-01: UTMs live in the separate `sale_utms` table, keyed by transaction_id.
- D-02: `utm_campaign` carries the campaign NAME (used for matching with Facebook data).
- D-03: `transaction_id` is the unique idempotency key.
- D-04: repeated ingestion of the same transaction must UPSERT (status transitions such as APPROVED -> REFUNDED must overwrite).

CRITICAL — why `created_at` matters: `src/app/api/metrics/route.ts` filters sales with
`.gte('created_at', startDate).lte('created_at', endDate)`. If imported historical sales are
inserted with the DEFAULT NOW(), every past sale collapses onto the import day and the whole
phase is useless. The mapper MUST derive `created_at` from the Hotmart order date.
</database_contract>

  <action>
Create `src/lib/hotmart.ts` implementing exactly the surface declared in the `<interfaces>` block above.

HARD CONSTRAINT — this module must stay pure and dependency-free: no imports at all (no `@/` alias imports, no `next/*`, no `@supabase/supabase-js`, no `date-fns`). It is compiled standalone by the verification harness, so any import breaks verification. No side effects at module load beyond the exported constants.

Implement, in this order:

1. `HOTMART_SALES_HISTORY_URL` — the string constant `https://developers.hotmart.com/payments/api/v1/sales/history`.

2. Internal helper `toCleanString(value: unknown): string | null` — returns a trimmed string for non-empty strings and for finite numbers (via String()), and `null` for everything else (undefined, null, empty string, whitespace-only string, objects, NaN).

3. Internal helper `toIsoDate(value: unknown): string | null` — normalises Hotmart date values:
   - number (or numeric string) `>= 1e12` is treated as epoch MILLISECONDS;
   - number (or numeric string) `> 0` and `< 1e12` is treated as epoch SECONDS and multiplied by 1000;
   - any other string is passed to `Date.parse`;
   - returns `new Date(ms).toISOString()` when the resulting timestamp is finite, otherwise `null`.

4. Exported `parseUtmString(raw: unknown): Omit<HotmartUtmRow, 'transaction_id'>` — Hotmart packs tracking data into the free-text `src`/`sck` fields, so support the three real-world shapes deterministically:
   - not a usable string (per `toCleanString`) -> all five fields `null`;
   - contains `=` -> strip a leading `?`, parse with `new URLSearchParams(...)` and read the keys `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` (each through `toCleanString`);
   - else contains `|` -> split on `|` and assign positionally in the order `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` (missing trailing positions become `null`);
   - else -> `utm_source` = the raw trimmed string, the other four `null`.

5. Internal helper `extractUtms(purchase, transactionId)` returning `HotmartUtmRow | null`:
   - read the tracking object from `purchase.tracking` (fall back to `purchase.origin`, then `{}`);
   - start from `parseUtmString(tracking.source_sck)`; if that produced five nulls, fall back to `parseUtmString(tracking.source)`;
   - any explicit `tracking.utm_source` / `utm_medium` / `utm_campaign` / `utm_content` / `utm_term` keys OVERRIDE the parsed values;
   - after that, if `utm_source` is still null use `toCleanString(tracking.source)`, and if `utm_content` is still null use `toCleanString(tracking.external_code)`;
   - return `null` when all five values are null (the route then skips the `sale_utms` write, mirroring the webhook), otherwise return the object including `transaction_id`.

6. Exported `mapHotmartItem(item: unknown): MappedHotmartSale | null`:
   - resolve `purchase` from `item.purchase` falling back to `item` itself;
   - `transaction_id` = first usable value of `purchase.transaction`, `item.transaction`, `purchase.order?.transaction`, `purchase.transaction_id`; if none is usable return `null` (unmappable rows are skipped, never inserted with a synthetic id — that would break D-03 idempotency);
   - `status` = first usable value of `purchase.status`, `item.status`, `purchase.transaction_status`, defaulting to the literal `UNKNOWN`, then `.toUpperCase()`;
   - `price` = `Number(...)` of the first usable value of `purchase.price?.value`, `purchase.full_price?.value`, `purchase.price`, `item.price`, defaulting to `0`; coerce `NaN` to `0` so the NOT NULL numeric column never receives NaN;
   - `created_at` = first non-null result of `toIsoDate` applied to `purchase.order_date`, `purchase.approved_date`, `purchase.date`, `item.order_date`, `item.creation_date` — null when none parse;
   - `utms` = `extractUtms(purchase, transaction_id)`.

7. Exported `dedupeMappedSales(items: MappedHotmartSale[]): MappedHotmartSale[]` — collapse repeated `sale.transaction_id` values keeping the LAST occurrence, preserving first-seen ordering. This is required because Supabase/Postgres `ON CONFLICT DO UPDATE` fails with "cannot affect row a second time" if one batch contains the same key twice.

8. Exported `extractPageInfo(payload: unknown): PageInfo` — read `payload.page_info?.next_page_token` (falling back to `payload.next_page_token`) through `toCleanString`, and `payload.page_info?.total_results` (falling back to `payload.total_results`) converted with `Number` and returned only when finite, otherwise `null`.

9. Exported `buildSalesHistoryUrl(params)`:
   - build from `HOTMART_SALES_HISTORY_URL` using `new URL(...)` and `url.searchParams.set(...)` — never string concatenation of caller input (prevents query/parameter injection);
   - always set `start_date` and `end_date` to `String(params.startDateMs)` / `String(params.endDateMs)` (Hotmart expects epoch milliseconds);
   - always set `max_results` to `String(params.maxResults ?? 50)`;
   - set `page_token` only when `params.pageToken` is a non-empty string (the key must be ABSENT otherwise);
   - return `url.toString()`.

Type-safety note: the module runs under `strict: true`. Accept `unknown` at the boundaries and narrow with local record helpers (e.g. a `asRecord(value: unknown): Record<string, unknown>` helper returning `{}` for non-objects). Do not use `any`, and do not use `@ts-expect-error`/`@ts-ignore` — `npm run lint` uses eslint-config-next and will flag `any`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hotmart REST API -> application | Third-party JSON of arbitrary shape enters the process. Every field is untrusted input. |
| Application -> Supabase (Postgres) | Mapped values cross into persistent storage via the service-role client. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Tampering | `mapHotmartItem` in `src/lib/hotmart.ts` | mitigate | Explicit allow-list field mapping only. The raw Hotmart item is never spread/`Object.assign`-ed into a DB row, so an attacker-controlled extra key (e.g. `id`, `created_at` override on another table) cannot reach Postgres. |
| T-06-02 | Tampering | `price` / `status` coercion | mitigate | `price` forced through `Number()` with a NaN->0 guard (column is `NUMERIC NOT NULL`); `status` forced through `toCleanString` + `toUpperCase` with an `UNKNOWN` default (column is `TEXT NOT NULL`). Prevents null/NaN constraint failures aborting an entire import batch. |
| T-06-03 | Tampering | `buildSalesHistoryUrl` | mitigate | URL assembled with `new URL` + `searchParams.set`; caller input is never concatenated into the query string, so parameter smuggling (`&access_token=`) is impossible. The host is a hard-coded constant, not env-driven — no SSRF pivot. |
| T-06-04 | Denial of Service | Batch upsert of one API page | mitigate | `dedupeMappedSales` removes duplicate conflict targets that would otherwise abort the whole `ON CONFLICT DO UPDATE` statement; `max_results` defaults to 50, bounding per-request memory. |
| T-06-05 | Information Disclosure | `src/lib/hotmart.ts` | mitigate | Module reads no `process.env` and holds no credentials; the access token stays exclusively in the server route (plan 06-02). The module is import-safe from any context. |
| T-06-SC | Tampering | npm installs | mitigate | This plan installs NO packages (Node built-ins + existing TypeScript only). No `npm install` is permitted; if the executor believes a dependency is needed, stop and escalate instead of installing. |
</threat_model>
